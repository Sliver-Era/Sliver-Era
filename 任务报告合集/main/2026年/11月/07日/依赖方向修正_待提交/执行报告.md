## 三、关键实现说明

1. **中立数据契约**
   - 相机 / 光照 / 雾 / 光源快照 / 场景聚合五个结构是纯数据（零图形 API），场景描述归系统层；
   - 渲染层在原路径 `src/render/Scene/场景数据.h` 留转发头（与 `src/render/Mesh/网格数据.h` 承接
     `Mesh_Loader` 的方式同构），因此 `渲染器.h`、`局部渲染命名空间使用.h` 与全部既有调用方零改动，
     且类型仍只有一处定义。
2. **资产缓存 / 粒子 / 场景装配**：整文件搬迁、接口签名与语义不变，仅改 include 与模块注释。
   `particle_gpu::emit / step_resident` 与 `friend` 声明保留在渲染层内部（现为层内授权）。
3. **版本锚点**：渲染层构建期对系统层与 Foundation 双层注入 `/FI`；系统层只剩 Foundation 一层。
   锚点头的 C 兼容修复是本次构建暴露的真问题 —— 渲染层就地编入的 SDL3 `.c` 也会收到 `/FI`，
   原锚点头含 `namespace`，纯 C 编译必然失败。
4. **对外接口引号缺陷**：`set(X ${Y})` 在 `Y` 为空串时会取消定义 `X`；系统层首次被上层
   `byjy_jieru_xiaceng()` 接入才暴露。

## 七、追加（同日）：删除 EngineFoundation 对外面的 `external` 伞根

### 7.1 判定

`BYJY_ENGINE_FOUNDATION_OUT_INC` 原为三条：项目根、`external/Json`、`external`（伞根）。
全仓检索 `#include <Json/...>`、`#include "external/..."`（项目根相对）：

- 命中只有渲染层两处 `#include "external/stb/..."`，解析基准是本层私有根 `Engine/EngineRenderer/external`，与 Foundation 无关；
- 没有任何代码依赖 `Engine/EngineFoundation/external` 这个伞根。

结论：伞根是历史残留（早期用于放开 `Json/...` 形式包含），无人使用，删除不影响任何编译单元。

### 8.5 使用方式

```cmake
# Engine/版本锁.cmake
set(BYJY_LOCK_EngineFoundation_Debug   "e046a4cd8ff3")   # 停在旧版
set(BYJY_LOCK_EngineSystem_Release    "")                # 跟随最新
```

- 锁空：跟随该层 `out/build/x64-<配置>`，行为与改造前一致。
- 锁非空：从 `Engine/版本缓存/` 取该版本的 include + lib（Renderer 还带 shaders），下层源码怎么改都不影响。
- 锁不存在：配置期 `FATAL_ERROR`，提示先构建该层 / 清空锁 / 换哈希。

### 9.3 边界说明

多配置支持的是「**本层自己**被 VS 生成器按配置正确构建」。下层产物仍按
`<层>/out/build/x64-<配置>` 约定定位（由 Ninja 双预设产出）；把某一层改成 VS 生成器后，
它的产物落在单棵树的 `lib/<Config>/` 下，不再是上层期望的 `x64-<配置>` 目录，
因此**跨生成器混用不在支持范围**——要么全链 Ninja 双预设，要么各层都用自己的多配置树并同步调整定位约定。

## 十、追加（同日）：支持跨生成器混用

第十节之前，上层只认 `<层>/out/build/x64-<配置>`（Ninja 布局）。本次让上层兼容
「下层由 Visual Studio 生成器构建」的布局，使 VS 一键构建的下层也能被复用。

### 10.1 产物布局

| 生成器 | 库 | 头快照 |
| --- | --- | --- |
| Ninja（双预设） | `<树>/lib/<层>.lib` | `<树>/include/Engine/<层>/...` |
| Visual Studio（单树双配置） | `<树>/lib/<配置>/<层>.lib` | `<树>/include/<配置>/Engine/<层>/...` |

三层（Foundation / System / Renderer）的 `IncludeSnapshot` 目标在多配置生成器下改为导出到
`<树>/include/$<CONFIG>`，否则 Debug / Release 会互相覆盖（两份锚点哈希不同）。

### 10.2 定位与锚点

| 位置 | 改动 |
| --- | --- |
| `cmake/版本工具.cmake` | `byjy_banben_jiexi()` 先试 Ninja 布局，缺失再扫 `out/build/*` 找 `lib/<配置>/<层>.lib`（多棵树取库文件最新者），头快照随之为 `include/<配置>`；`byjy_banben_duqu()` 改为直接接收头快照根 |
| 四份 `cmake/接入下层.cmake` | 分配置锚点优先使用调用方给出的 `<覆盖变量>_INCLUDE_DEBUG/_RELEASE`（与 `OUT_LIB` 同构的列表），不再只能靠库路径 `../..` 反推 |
| 四层 CMakeLists | 传入分配置头快照根；发布目标改传 `SNAPSHOT_ROOT` / `LIB_FILE`（`$<TARGET_FILE:...>`），VS 树也能正确发布到版本缓存 |
| `cmake/发布版本缓存.cmake` | 新增 `SNAPSHOT_ROOT` / `LIB_FILE` 参数（缺省仍按 Ninja 布局） |
| `Application/Test/CMakeLists.txt` | 着色器目录推导兼容两级（Ninja）与三级（VS）上溯 |

### 10.3 优先级

同一层同时存在 Ninja 的 `x64-<配置>` 树与 VS 树时，**优先 Ninja**（候选①），保证既有双预设流程不受影响；
只有 Ninja 树缺失时才回退到 VS 树。
