## 三、核心接口

### 3.1 `Entity`

```cpp
struct Entity
{
    uint64_t value = 0;                 // generation(高32) | index(低32)
    uint32_t index(void) const;
    uint32_t generation(void) const;
    bool empty(void) const;             // value == 0
    bool operator==/!=(const Entity&) const;
};
Entity entity_make(const uint32_t& index, const uint32_t& generation);
```

template <Component_Type C, typename... Args> C* component_add(Entity, Args&&...);

## 四、实现细节与关键决策

1. **实体表自持，不复用 `Object_Pool`**：`std::vector<Entity_Record>` + `Number_Pool<uint32_t>`；`set(1)` 预留槽位 0，使 `Entity{}`（值 0）天然无效。
2. **记录表按目标槽位扩展**：实体槽位从 1 起，扩展必须用 `while (index >= records.size()) records.push_back({})`，不能只 push 一次（实现中已修正该越界崩溃）。
3. **代际推进时机**：销毁实体时 `generation++`（回绕为 0 时修正为 1）；复用槽位直接沿用递增后的代际，旧句柄因此永久失效。
4. **`clear` 不丢代际**：清空时对全部记录 `alive=false / mask=0 / generation++`，再重置槽位分配器；若清空记录表会让旧句柄在重建时“复活”，故保留记录并推进代际。
5. **组件存储**：`Component_Storage_Impl<C>` 内部 `Object_Pool<C, uint32_t>`，构造注入投影器 `[](const C& c){ return c.owner; }`；键为实体槽位，哈希模式 O(1)。
6. **组件类型约束**：`Component_Type` 为概念约束 —— 派生 `Object`、可移动、`owner` 可赋值。组件固定成本约 16B 基类 + 4B owner（对齐后约 24B）。
7. **类型擦除与注册**：`type_index → unique_ptr<Component_Storage>`；首次注册分配 64 位掩码中的一位，超过 64 种组件注册失败并 `logger.error`。
8. **重复添加保护**：`component_add` 先查后建，已存在返回 `nullptr`，不覆盖原值。
9. **删除走 `try_unload`**：`component_remove` / 级联销毁使用 `Object_Pool::try_unload`，缺失键静默失败，不刷告警。
10. **交集遍历**：`each<C1,C2>` 以较小的组件池为驱动，按 `owner` 在另一池 `find`，回调前用 `entity_from_index` 校验归属实体存活。
11. **命令缓冲语义**：`entity_create` 立即执行（需返回句柄）；仅销毁与组件增删进入缓冲；`flush` 按记录顺序提交。命令闭包捕获组件值，`std::function` 要求组件可拷贝。
12. **不提供系统调度**：ECS 只负责数据与查询；行为为普通函数（接收 `ECS_Store&`），由帧循环显式调用。若后续需要编辑器/重排/并行调度，再作为独立可选层引入。
13. **错误处理**：全链路无异常；无效句柄返回 `nullptr/false`，资源分配使用 `new (std::nothrow)`。
14. **线程模型**：非线程安全，约定在单线程逻辑帧内使用。

## 六、实现过程中修复的问题

1. `局部命名空间使用.h` 缺少 `<typeindex>`，导致 `using std::type_index` 编译失败 → 已补充头文件。
2. `Entity_Table::entity_create` 原只 `push_back` 一次，槽位从 1 起时索引 1 越界（Debug STL 断言崩溃）→ 改为按目标槽位循环扩展。
3. 命令缓冲测试以 `int` 隐式构造 `explicit Health(int)` 失败 → 测试改为显式传入 `Health(30)`。
4. `ECS_Store::clear` 若直接清空记录表会导致旧句柄在重建时复用同代际 → 改为保留记录并推进代际。

## 七、已知限制与后续

- 组件固定开销：`Object` 基类 16B + owner 4B + 哈希表节点；规模上限适合玩法层，10 万级需换 sparse-set/archetype。
- 最多 64 种组件类型（64 位掩码）。
- 组件必须派生 `Object` 且自带 `owner`；若后续做“外部键注入/元数据外置”，可去掉 owner 字段与基类。
- 遍历中直接增删仍会失效迭代器/引用；必须使用 `Command_Buffer`（已在注释中约束）。
- `Command_Buffer` 的命令闭包要求组件可拷贝（`std::function` 限制）。
- `ECS_Store::clear` 保留组件类型注册与掩码位分配，不清空 `next_bit`。
- 交集遍历目前为双组件；N 组件可按同样模式扩展。
- 不提供系统调度：行为为普通函数，由帧循环显式调用；AI/效应系统待其机制确定后再以独立模块接入。
- `EngineRenderer` 的 BOM 阻塞需另行修复后才能重建顶层 `EngineTests.exe`；碰撞模块的进行中改造也需先恢复可编译，才能重链 `TestSystem.exe`。
