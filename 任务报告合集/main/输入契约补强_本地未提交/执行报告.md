## 二、修复中发现并修正的一处真实漂移

`输入类型.h` 的名称表定义 `0`→类内 27、`9`→36（0~9 连续 27..36），
而旧版 `系统输入桥.cpp` 把 `SDL_SCANCODE_0` 写成 **36**、`1~9` 写成 27..35。

后果：**所有数字键整体错位**——按 `0` 产出的是 `9`，按 `9` 产出的是 `8`。因为没有任何用例断言过 `0`～`9` 的真实编号，这个错误一直静默存在。上一轮的桥用例恰好断言了错误值（`0 == 36`），所以一直"通过"。

本次修正为常量引用后，该用例立即失败并暴露问题；现已改为断言 `INPUT_KEY_0`，并把 `0`~`9` 的编号写入 T1/T2 的表驱动守卫。

**这正是 F1 想解决的风险，且已经真实发生过一次。**

## 六、已知取舍与边界

1. **同帧按键顺序仍被抹平**（N2）：命令在帧末统一求值，同帧"先按 S 再按 Ctrl"也命中 `Ctrl+S`。物理上 Ctrl 确实是先按下的单键；改为逐边沿求值会重新引入"修饰键单键先于组合开火"。属配置语义问题，不是缺陷。
2. **`repeat` 不参与组合抑制**：重复沿走独立第三轮，不受 `consumed` 影响。因此"按住 Ctrl 不放 + 连按 S"会连续产出 `Ctrl+S`（`S` 是新的按下沿，不是重复沿），而"按住 S 不放"只产出一次 `Ctrl+S`（S 的重复沿不进 `presses`），除非该绑定同时开了 `repeat`。
3. **模态归属为弱校验**：中转站不校验 sender 身份，伪造 sender 名仍可弹栈。本次只防误用，不防恶意；真校验需协议级改动。
4. **`axes` 仍无渲染层生产者**：本次只让缺口可见。手柄/模拟量需游戏层自建 `Input/Raw` 投递。
5. **`cursor_get` 为最近一帧快照**：由任意对象的 `RawFrame` 触发刷新，与焦点对象无关；若一帧内没有 Raw（如模态闸门丢弃），则位置保持、增量归零。
6. **桥的翻译覆盖范围**：仅覆盖中立表内已登记的键位；媒体键、`KP_EQUALS` 等未登记扫描码仍返回 0 并被静默丢弃（无告警）。这是可接受的，因为中立表本身不承诺这些键。

## 七、待补充（构建环境注意事项，沿用上一轮）

1. `cmake` / `ninja` 未入 PATH，需用 VS 自带完整路径。
2. **`TMP` / `TEMP` 必须指向纯 ASCII 路径**，否则 MSVC 报 `D8050` / `LNK1104`（用户名含中文时）。
3. 改 EngineSystem 头后必须重建 EngineRenderer 的 Debug 与 Release 两套树，否则 Test 工程版本锁拒绝配置。
4. **版本锚点会随每次 EngineSystem 构建churn**。下游只需**重新链接**即可对齐，不必重新编译；出现 `LNK2001 byjy_stamp_engine_system_<hash>` 时按「System → Renderer → 子测试树 → 聚合」顺序重链一遍。
5. 测试工程四棵构建树：先重建 `tests/{Foundation,System,Renderer}`，再重建聚合 `Application/Test`，否则 `EngineTests.exe` 仍链接旧静态库。
6. 聚合全量在本机极慢（单个渲染套件数分钟），日常回归建议直接用 `TestSystem.exe` / `TestRenderer.exe` 的过滤器，而不是 `EngineTests.exe` 全量。
7. **改名 / 移动头文件后必须重新 configure**（不是只 build）：`源文件列表.cmake` 与头快照导出列表在 configure 期生成，只 build 会保留旧路径，导致快照里出现"旧目录被删空、新目录没生成"的假成功。本轮 `Common → common` 改名即踩到此项，重 configure 后恢复正常。
